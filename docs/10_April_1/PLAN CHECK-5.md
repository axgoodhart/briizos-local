## Findings

This check uncovered **two major prior-art systems** that the PLAN-1 / PLAN-2 plan was on a collision course with. Both are serious enough to rewrite the plan.

### Finding 1 — "Projects" is already a concept in the codebase, and it is not what the user means

`firestore.js` already exports `subscribeProjects`, `getProjects`, `upsertProject`, and `deleteProject`. All four operate on the `organizer` collection with `type === 'project'`. They are the backing store for the "Projects" tab of `OrganizerModal`, and `OrganizerContext.projects` is exactly `items.filter(i => i.type === 'project')`. These Organizer "projects" are metadata buckets (deadlines, importance, tasks, milestones) — conceptually closer to Jira epics than to the user's request of "launchable mini-app".

If I had proceeded with PLAN-1 / PLAN-2 unchanged, I would have either (a) replaced these four helpers, silently breaking the Organizer Projects tab, or (b) added an import collision that would have broken the build. Either way, a "half of the job was done yesterday and is not in memory right now" style disaster.

**Plan adjustment**: do not reuse the word "project" in code identifiers or collection names. The user's own prompt refers to the items as **canvases** ("store canvases generated by the onboard AI"), which is also the word the existing transient canvas system already uses. We adopt "canvas" as the code-level and user-visible name.

### Finding 2 — A full canvas persistence system already exists, via Electron IPC to a flat-file store

There is already a working canvas pipeline:

- **Storage**: `electron/agent-config.js` exposes `DIRS.canvas = {appData}/briizOS/canvas`. HTML files live there as `{timestamp}-{slug}.html`.
- **Write**: `ipcMain.handle('canvas-save', (event, title, html))` — writes a full HTML file and returns `{ filename, path }`. Reachable from the renderer as `window.api.canvasSave(title, html)`.
- **List**: `ipcMain.handle('canvas-list')` — returns `[{ filename, title, size }]` sorted newest-first.
- **Load**: `ipcMain.handle('canvas-load', (event, filename))` — returns raw HTML string.
- **AI tools** (`src/lib/tools.js` lines 307-371): `openCanvas` (writes + opens), `updateCanvas` (fires an update event), `listCanvases`, `loadCanvas`.
- **Display**: `LiveCanvas.jsx` — the draggable floating iframe that shows the currently-open canvas, driven by `briizos-canvas` DOM events dispatched from `App.jsx` (lines 375-393).

In plain English: **the AI can already author, save, list, and load canvases.** What is missing is:

- A **user-facing UI** to browse the saved-canvases library (today only the AI can `listCanvases`).
- **Metadata beyond raw HTML**: there is currently no storage for a canvas's form factor, a non-slug-derived display name, tags, or user edits.
- A **create flow for non-AI canvases**: the user cannot yet create a canvas from raw code or from a URL. Only the AI-authored path exists (via `openCanvas`).
- **Delete / rename** affordances at the IPC layer (`canvas-delete`, `canvas-rename` do not exist).
- **Tile**, **Widget**, and **Hybrid** form factors — the only rendering path today is the transient floating `LiveCanvas`.

If I had proceeded with PLAN-1 / PLAN-2 (Firestore-based "projects"), I would have stood up a completely **parallel** canvas storage system next to the existing flat-file one. The AI would save to flat files via `window.api.canvasSave`, and the user would see a popover full of Firestore docs. They would never overlap. That would be a catastrophe of the exact kind stage-pass exists to prevent.

**Plan adjustment**: build on top of the existing canvas IPC. Do not touch Firestore at all for this feature.

### Finding 3 — SyncContract §2 explicitly forbids using the `panels` collection for anything except `type == "note"`

SyncContract line 20: `users/{uid}/panels/{id}` (notes only: `type == "note"`). PLAN-1's fallback of storing a `type="project"` doc in `panels` was already out of bounds. PLAN-2's Shrink 3 had pivoted to a desktop-only collection, but Finding 2 now makes any Firestore storage unnecessary.

### Finding 4 — There is no existing keybinding on `Cmd/Ctrl+Shift+C`

Actually there is — `Cmd/Ctrl+Shift+V` toggles Canvas (`canvasOpen`) in `App.jsx` (lines 343-346). And `Cmd/Ctrl+Shift+B/A/O/C/N/V` are all taken. The next free letter that connotes Canvases is `Cmd/Ctrl+Shift+K` (K for "library"/"kiosk"). Use `K`.

### Finding 5 — `cowork/10_April_1/` is freshly created today

No earlier dated scratchpads exist for this exact task in `cowork/`, so there is no half-done work to rescue.

## Plan adjustments (carry into execution)

The revised plan is substantially smaller than PLAN-1 / PLAN-2 because Finding 2 eliminates the need for a new storage layer. What remains:

### 1. Terminology

- **Code-level name**: `canvas` / `canvases`. No `project*` identifiers in any new code.
- **User-visible name**: "Canvases" on the Control Bar toggle.
- **Panel type**: `canvas` (confirmed unused — `renderPanel` switch covers `sources | interaction | tasks | actiondeck`).

### 2. Storage — extend, don't replace

- Keep using the existing Electron IPC + flat-file canvas store at `{appData}/briizOS/canvas`.
- Store per-canvas metadata (form factor, last-opened, displayName override, source type) in a **sidecar file**: `{filename}.meta.json` next to each HTML file. This avoids corrupting the HTML with embedded comments and keeps the existing `canvas-list`/`canvas-load` flow working unchanged.
- **New IPC handlers** in `electron/main.js` + `electron/preload.js`:
  - `canvas-delete(filename)` — deletes HTML + sidecar.
  - `canvas-save-meta(filename, meta)` — writes sidecar JSON.
  - `canvas-load-meta(filename)` — reads sidecar JSON, returning `{}` if missing.
  - `canvas-rename(oldFilename, newTitle)` — rename HTML + sidecar, returns new filename.
- **Extend `canvas-list`** to also read each canvas's sidecar and merge `meta` into the returned record, so one call gives the popover everything it needs (filename, title, size, formFactor, source, createdAt).

### 3. New files to create (replacing PLAN-1 / PLAN-2 file list)

- `src/components/canvases/CanvasesPopover.jsx` — the tooltip-style folder anchored under the Control Bar button. Lists canvases from the IPC, empty state with central "+", bottom-right "+" when non-empty.
- `src/components/canvases/CanvasesPopover.css` — dark glassy popover styling, tail pointer.
- `src/components/canvases/CanvasCard.jsx` — per-canvas row (name, form-factor badge, click-to-open, context menu with rename/change-form-factor/delete).
- `src/components/canvases/NewCanvasFlow.jsx` — the 3-option create flow (AI / Code / URL) + name input. On confirm, routes:
  - **AI**: creates an empty canvas, opens it in floating mode, emits a `startCanvasSession(canvasId)` hint to the chat panel so the user can prompt the AI to fill it in.
  - **Code**: creates an empty canvas with a minimal HTML skeleton and opens it in floating mode with an editable textarea overlay (HTML/CSS/JS tabs).
  - **URL**: prompts for a URL, creates a canvas whose HTML is `<!doctype html><iframe src="URL" style="...">`.
- `src/components/canvases/NewCanvasFlow.css`
- `src/components/canvases/CanvasTile.jsx` — for Panel Tile form factor. Renders an iframe with `srcDoc` from the canvas's HTML. Minimal header with name + close.

Add to `layoutRow.workspace` (via `updateWorkspace`):

### 9. Keyboard

- `Cmd/Ctrl+Shift+K` toggles the Canvases popover.
- Escape order: closes CanvasesPopover first if open, then the existing stack.

### 10. Risks and mitigations

- **Sidecar file consistency**: if a canvas HTML file is deleted externally, its sidecar is orphaned. Mitigation: the new `canvas-list` handler ignores orphaned sidecars and only returns canvases whose HTML file exists.
- **Metadata for pre-existing canvases**: canvases that were saved by the AI before this change will have no `.meta.json`. Mitigation: `canvas-load-meta` returns `{}` on miss, and the UI treats missing metadata as `{ formFactor: 'float', source: 'ai' }`.
- **Popover clipping**: `.controlBar.closed` uses transitions that might clip a popover. Mitigation: the popover only renders when the Control Bar is open (the trigger button is in the Control Bar anyway), and the parent bar is given `overflow: visible` when open.
- **Single-canvas floating limitation**: accepted for this pass; documented.
