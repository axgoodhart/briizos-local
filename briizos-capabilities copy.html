How to read this document

This atlas documents every user-facing capability of briizOS.local: what you see, what code produces it, what logic shapes the results, and — most importantly — where the safe, targeted adjustment knobs are.

Conventions used throughout:

  • src/App.jsx:885 — a citation: the file (path relative to the repo root) and line number where the described behavior lives. Line numbers are accurate as of the generation date above; they drift as code changes, but the function names cited alongside them will keep you oriented.
  • Green boxes are adjustment recipes: concrete copy-paste-level edits you can make (or hand to a dev) with confidence about the blast radius.
  • Amber boxes are cautions — places where a seemingly small edit touches sync rules, the agent's tool contract, or data on disk.

Every recipe states its blast radius: what else the change can affect. "Local only" means the change affects rendering/behavior on this machine and nothing stored or synced.

The stack, in plain language

briizOS.local is an Electron desktop app: a Chrome browser window (the "renderer") glued to a Node.js process (the "main process") that can touch your disk, run the AI agent, and talk to the cloud.

LayerWhat it isReliability / visibility / footprint
Renderer
src/		 A React app (built by Vite) — everything you see: panels, overlays, chat. It has no direct disk or network power of its own; it asks the main process over IPC (inter-process calls). Crashes here show as a broken window but never corrupt data. Everything it does is observable in the Log section (see Logging).
Preload bridge
electron/preload.js		 The single, explicit doorway (363 lines) between renderer and main process. Every capability the UI has is a named function on window.api. If a function isn't listed here, the UI physically cannot do it. This is your security perimeter — auditing this one file tells you the app's entire reach.
Main process
electron/		 Node.js. Owns the local SQLite database, the filesystem tools, the GitHub/Drive/weather integrations, and — since the langchain branch — the AI agent itself, running in-process (no Python, no local server). ~99 IPC handlers registered in electron/main.js plus the data service in electron/local-data-ipc.js.
Local database
briizos.db		 One SQLite file (via better-sqlite3) with 48 tables — tasks, organizer items, journals, chat threads, agent memory, logs, everything. Schema defined in electron/local-data/schema/001–008_*.sql. This is the app's primary source of truth. It works fully offline. Inspect it anytime with npm run db:studio.
Cloud
Firebase / Firestore		 Login (email/password) plus selective sync: tasks, organizer, and retained text mirror to Firestore under users/{uid}/… per the SyncContract. A cloud gateway also lets remote commands reach this machine. Cloud being down degrades to local-only; nothing user-visible breaks except sync and remote commands.
AI agent
electron/agent/		 A LangGraph.js "ReAct" agent (think → call a tool → observe → repeat) living inside the main process. Talks to Anthropic, OpenAI, or Google models depending on your model picker choice. Every AI call and tool execution is logged. Conversation state persists in briizos.db, so restarting the app keeps thread context.

Workspace shell & tiling layout

What you see

A header (wordmark, control dock, date/time/weather), and below it a row of resizable columns, each holding one or more stacked panels. Panels can be dragged onto each other (stack), or to an edge (split), fullscreened, hidden, and reopened. Floating surfaces (Notes drawer, Media panel, a torn-off Journal, floating Canvases) hover above the tiles. Overlays (Organizer, Calendar, Briiztorm, Dashboard) cover the whole window.

How it works

  • Panel registry. Eight panel types exist. The mapping from type name → React component is a single switch: src/App.jsx:885 renderPanel() — sources, interaction (chat), tasks, media, journal, notefalls, forest, canvas.
  • Layout state. A "v2 LayoutRow" — columns, each with sized panels, plus hiddenPanels and a workspace bag for overlay geometry — managed by src/hooks/useLayout.js:24. Loaded from SQLite at startup (window.api.localData.workspace.getLayout(), line 44) and auto-saved with a 500 ms debounce (line 87). v1 flat layouts are migrated on load (line 50).
  • Drag & drop. src/hooks/useLayout.js:165 movePanel(): dropping on a panel's center stacks; dropping on top/bottom/left/right splits. Rendering and drop zones live in src/components/layout/TileLayout.jsx:226.
  • Workspace persistence. Overlay open-states and floating rects (notes drawer, media panel, journal float, open canvases, Theme Studio width) restore once after layout load — src/App.jsx:279 — and persist on change — src/App.jsx:299.
  • Self-healing. On startup the shell removes retired ActionDeck panels (src/App.jsx:256) and orphaned canvas tiles whose files were deleted (src/App.jsx:707).
Recipe — add a brand-new panel type
  1. Build the component (copy the shell of src/components/notefalls/NotefallsPanel.jsx — it's a clean example of a <div class="panel"> with header + content).
  2. Add a case 'mytype': return <MyPanel />; branch inside renderPanel() at src/App.jsx:885.
  3. Give it an opener: copy the 8-line openForestPanel pattern at src/App.jsx:409, changing 'forest' to 'mytype'. Blast radius: local only — layouts persist per-machine.
Recipe — change a panel's default width

Every opener calls addPanel({ id, type, size: 25, visible: true }) — the size is percent of window width. Change the 25 in the relevant opener (src/App.jsx:348, 405, 414, 427). Blast radius: only newly-opened panels; existing layouts keep user-resized values.

Logging & observability

What you see

The Log section at the top of the Sources panel: a reverse-chronological feed of entries like July 19, 2026 · 09:14 · [info:journal] Journal popped out. It shows the most recent 80 entries live.

Doc drift

CLAUDE.md's hard rule #1 references src/components/LogPanel.jsx — that file no longer exists. The live log UI is the Log section inside src/components/SourcesPanel.jsx:371, fed by the same logger. The rule's intent (every meaningful action produces a visible log entry) is intact; the file reference is stale.

How it works

  • One logger, three destinations. src/lib/logger.js — every logger.info('category', 'message', data) call simultaneously: (1) prints a structured line to the terminal (sendToTerminal, line 88 — the [HH:MM:SS] [category] LEVEL message {data} format from CLAUDE.md rule 3), (2) appends to an in-memory ring buffer that the UI subscribes to (addToBuffer, line 128; subscribeLogs, line 157), and (3) writes to the SQLite logs table (writeToLocalDb, line 101).
  • Category routing. A CATEGORY_MAP (line 27) normalizes log types; entries prefixed agent./tool. are tagged as agent-sourced, system./sync./firestore./auth./error. as system-sourced (lines 63–66).
  • Electron-side logs merge in. Main-process logs (from electron/logger.js) hydrate into the same renderer buffer (hydrateTerminalLogs, line 215), so agent and database activity appears in the same feed.
  • Debug mode. npm run dev:debug launches Electron with LOG_LEVEL=debug (package.json scripts), surfacing the verbose logger.debug tier everywhere.
Recipe — see more (or fewer) log rows

Two independent caps: the UI keeps 80 rows — change the 80 in logData.slice(0, 80) at src/components/SourcesPanel.jsx:318 — and the buffer keeps 500 — change LOG_BUFFER_MAX at src/lib/logger.js:113. Blast radius: local only; SQLite retention is unaffected.

Recipe — filter what the buffer accepts

shouldBufferLog() at src/lib/logger.js:123 is the gatekeeper between "logged" and "shown in the panel." Add a category or level check there to mute noisy categories from the UI without losing them from terminal/SQLite.

Theme system & Theme Studio

What you see

Built-in themes (Dark Neon, Antarctic Teafog, Great Wave, Sherbert Sakura, …) selectable from the Dashboard, plus a dockable Theme Studio side panel (300–480 px wide) where you click any surface in the live app and restyle it — colors, fonts, borders, radii.

How it works

  • Provider. src/theme/ThemeProvider.jsx applies the active theme as CSS variables and holds the edit session (with an unsaved-changes guard — requestClose used at src/App.jsx:317).
  • What's themeable. src/theme/themeRegistry.js defines 16 COMPONENT_IDS (Application, Tasks, Chat, Journals, Forest, …) and a TARGET_REGISTRY of surfaces (header, wordmark, canvas, …) each with allowed properties. Components opt in via data-theme-role / data-theme-component attributes in their JSX (see them on the app root at src/App.jsx:950).
  • Color math. src/theme/chromap.js is a full OKLCH color engine — theme generation (harmony, temperature, saturation, contrast, glow) computes perceptually-even palettes rather than hand-picked hex lists.
  • Safety. Every theme document is validated against src/theme/themeSchema.js — including an UNSAFE_CSS regex (line 5) that rejects url(), javascript:, @import etc., so a malicious theme file can't inject behavior. The Electron side re-validates on save (electron/theme-library-validation.js). This layer has real test coverage: npm run test:theme.
  • Persistence. Theme library and selection live in the SQLite settings table under ui_theme / ui_theme_library (electron/local-data-service.js:20 SETTING_KEYS).
Recipe — add a built-in theme

Copy any one-line entry in src/theme/builtInThemes.js (e.g. the winterbloom line), give it a unique id, label, description, and mode: 'dark'|'light', and define its tokens alongside the others in the same file. Blast radius: local only; validated on load, so a malformed entry falls back rather than breaking the app.

Recipe — make a new surface themeable

Add a data-theme-role="…" data-theme-component="…" pair to the element's JSX (any existing panel header shows the pattern), then register the role in TARGET_REGISTRY at src/theme/themeRegistry.js:9 with its allowed property list. The Theme Studio click-picker discovers it automatically via observeThemeSurfaces.

AI chat (Interaction panel)

What you see

The chat panel: streaming responses, visible tool-call chips while the agent works, thread titles that auto-generate, follow-up suggestions after each turn, a model picker, selectable animated backgrounds, and confirmation prompts (the Margerin pill) when the agent wants to do something destructive. Files selected in the Sources panel ride along as context.

How it works

  • UI: src/components/InteractionPanel.jsx renders messages/stream/toolcalls; the animated backgrounds are plain HTML files listed in its CHAT_BACKGROUNDS array (line 1) and loaded from public/assets/backgrounds/.
  • Brain of the UI side: src/hooks/useChat.js:141. sendMessage() (line 554) builds the request (attaching selected-file context, line 55), calls window.api.langgraphStreamMessage(...), and handleStreamEvent() (line 322) consumes the SSE-style event vocabulary — text, tool_call_start, tool_result, thread_title, values, end, error.
  • Modalities: the panel can run in different thread kinds (threadKindForModality, line 82) — regular chat vs. specialized flows like prioritization (buildPrioritizeAddendum, line 116 feeds the prioritizer skill).
  • Confirmations & clarifications: resolveConfirmation() (line 727) resumes a paused agent run after you approve/reject; clarifying questions from the agent surface as pendingClarification (line 151).
  • Suggestions: after each turn, finalizeAssistantTurn (line 524) can fetch follow-up suggestions (langgraph-fetch-suggestions IPC), toggleable via the suggestions_enabled setting.
Recipe — add a chat background

Drop a self-contained HTML file into public/assets/backgrounds/, then add { value: 'assets/backgrounds/MyBg.html', label: 'MyBg' } to the CHAT_BACKGROUNDS arrays in src/components/InteractionPanel.jsx:1 and src/components/overlays/DashboardOverlay.jsx:2 (the settings mirror — keep both lists in step). Blast radius: cosmetic, local only.

The in-process agent runtime

The langchain branch's headline: the AI agent moved from an external Python process into Electron's main process. Same event vocabulary, zero subprocesses — "no Python in the runtime path; no HTTP tool-bridge" (electron/agent/index.js:1).

Recipe — add a model to the picker

Copy any line in electron/built-in-models.js and edit the id/display name/caps — e.g. duplicate the Claude Sonnet line and set model: 'claude-sonnet-next'. The memory system's knobs live in the agent_config setting read by getConfig() at electron/agent/system-prompt.js:29 — memory: { enabled, injection_enabled, max_injection_tokens: 2000 }. Raising the token budget gives the agent more remembered context per turn at higher cost per message.

Tool system & permission gate

The agent acts on the app through ~50 named tools. Data reads run in the main process; anything that changes UI state or touches your files makes a round-trip through a renderer-side permission gate the model cannot bypass.

The two tool surfaces

  • Agent-side (main process): electron/agent/tools.js declares the tools the model sees — data writers (briizos_create_note:288, briizos_create_task:322, briizos_schedule_task:376…), data readers (briizos_list_tasks:543, briizos_get_schedule:674, the catch-all briizos_query_data:1014), filesystem (read_file:1038 … bash:1109, str_replace:1153), media (view_image:1203, present_files:1231), ask_clarification:1287, and a task sub-agent spawner:1456.
  • Renderer-side (the executor): src/lib/tools.js is the registry of actual handlers — 50 entries from getScheduleSummary (line 106) through panel manipulation (openPanel:1007, tilePanels:1067, focusMode:1095…), canvas ops (openCanvas:398), calendar ops (scheduleTask:746), and filesystem wrappers that check the blacklist before every IPC call (agentReadFile:214). Each entry declares requiresConfirmation, a description, parameters, and a handler.

The gate

  • Path: agent → bridge.js → IPC tool-bridge-execute → src/hooks/useToolBridge.js → ToolContext.executeTool — one canonical executor for chat, automation, and workers alike (src/App.jsx:193 comment).
  • Enforcement: src/context/ToolContext.jsx throws an unbypassable PermissionGateError — "the gate runs in the renderer, after the agent, immediately before the tool handler executes" (line 4).
  • Per-surface policy: src/lib/agentSurfaces.js maps each agent run's thread id to a policy (chat vs. background task vs. planner). Fail-closed: an unknown thread gets the most restrictive policy — ask-always, empty allowlist (line 12).
  • Command vetting: src/lib/permissions.js classifies shell verbs (rm, chmod, kill… destructive; ls, grep… safe) and maintains the filesystem blacklist checked by every file tool.
  • Your consent UI: confirmations render as the Margerin pill; in chat, approve/reject resumes the paused run via resolveConfirmation (src/hooks/useChat.js:727).
Recipe — make any tool ask before running

Flip its requiresConfirmation: false to true in its entry in src/lib/tools.js (each tool's first property — e.g. line 151 for searchNotes). Blast radius: that tool now pauses every surface (chat, automation) for approval — background automation runs will stall waiting on you, which is sometimes exactly what you want.

Recipe — add a new tool
  1. Add a registry entry in src/lib/tools.js — copy the compact searchNotes block (lines 150–178): key, requiresConfirmation, description, parameters, async handler.
  2. If the model should call it, mirror a declaration in electron/agent/tools.js (copy an adjacent name:/description:/schema: block).
  3. If it reads a new data domain, register it in electron/agent/data-catalog.js and run npm run tools:catalog to regenerate the docs the agent reads.

Agent skills & data catalog

Skills

Skills are markdown instruction packs injected into the system prompt when enabled (loader in electron/agent/system-prompt.js; toggled per-skill via the skills-toggle IPC and skills_config setting). Three custom skills ship in agent/skills/custom/:

  • day-planner — plans one calendar day from real events/placements/tasks/projects; hard rule: read the day with briizos_get_schedule before claiming availability (agent/skills/custom/day-planner/SKILL.md).
  • prioritizer — ranks Forest projects + tasks against deadlines/importance/effort; explicitly excludes organizer type: project records (agent/skills/custom/prioritizer/SKILL.md).
  • stylofact — drives the Stylofact pipeline (agent/skills/custom/stylofact/SKILL.md).

Plus ~45 public skills in agent/skills/public/ (summarize, deep-research, image-generation, …).

Data catalog

electron/agent/data-catalog.js is the source of truth for what the agent may read. Dedicated tools cover tasks/Forest/organizer/placements/schedule; everything else goes through the bounded reader briizos_query_data over 15 domains:

journalsnotefall_postscanvasesfilesconversationsmemoryrecorder_sessionsstylofact_projectsautomation_runsmediabriiztormworkspacesettingslogssystem_status

Reads are local, read-only, and logged as agent.data. The human-readable mirror electron/agent/DATA-CATALOG.md is generated — edit data-catalog.js, then npm run tools:catalog (checked in CI-style via tools:catalog:check).

Recipe — write your own skill

Create agent/skills/custom/my-skill/SKILL.md with the 4-line YAML frontmatter the others use (name, description, optionally user-invokable: true) followed by markdown instructions. It appears in the skills list (Dashboard → skills toggles) on next launch. Blast radius: prompt-only — a skill can only steer the agent toward tools that already exist behind the permission gate.

Tasks & decks

What you see

The Tasks panel: a task list where any task can carry subtasks ("steps"); a task with steps renders as an expandable deck of cards. An AI Deck Maker box turns a typed goal into a full deck — sometimes asking one clarifying question first — and auto-opens the result.

How it works

  • UI/state: src/components/TasksPanel.jsx + src/hooks/useTasks.js (reads via window.api.localData.tasks.list() → SQLite tasks + task_steps tables).
  • Vocabulary: statuses and priorities are validated centrally — electron/local-data-service.js:12: statuses pending, created, running, in_progress, active, waiting, deferred, completed, cancelled, blocked; priorities low, normal, medium, high, urgent.
  • Deck Maker: src/lib/deckMaker.js — one headless agent turn per round: goal → either { isDone: true, deckTitle, tasks[] } or { isDone: false, clarifyingQuestion }. The clarify loop stays on one thread so the agent keeps context, and the thread is registered fail-closed, text-only on the 'task' surface — the deck-making agent cannot call tools at all (file header, lines 1–15). Orchestrated by src/hooks/useDeckMaker.js.
  • Task log: every automation/AI touch appends to a per-task taskLog (src/lib/localTasks.js), visible on the card.
Caution

Task status/priority lists look like easy edits, but they're a shared contract: the agent's tool schemas (electron/agent/tools.js), the data catalog, Firestore mirrors (src/lib/firestore.js:119 normalizeTaskDoc), and the web app all speak them. Add a status only if you update all four surfaces.

Task automation & cloud workers

What it does

Flag a task for automation and the agent works it in the background: no steps → it asks the AI for a breakdown; steps exist → it resumes from the next unchecked one; all checked → it verifies completion and marks done or asks you (the decision tree in src/lib/taskAutomation.js:1).

How it works

  • Local pipeline: src/hooks/useTaskAutomation.js:1 documents the whole chain in its header: SQLite notifications → decision tree → window.api.langgraphSendMessage (the synchronous, non-streaming variant — background runs have no live UI) → in-process agent → tool calls back through the same permission gate → results written to the task's taskLog.
  • Worker pool: src/hooks/useAgentWorkers.js:1 runs AGENT_WORKER_COUNT = 3 concurrent workers that claim jobs from Firestore (src/lib/agentJobsFirestore.js — transactional claim so two devices never grab the same job; scoring/claim logic also mirrored in src/lib/firestore.js:966 claimNextAutomatedTask with heartbeats at line 1052).
  • Remote commands: electron/cloud-gateway.js polls Firestore every 15 s (POLL_MS), heartbeats every 60 s, holds a 3-minute lease — so a command issued from the web/mobile app runs on this machine via electron/automation-runner.js, with run lifecycle states accepted → queued → running → waiting_for_user → completed/failed/cancelled/expired/rejected (electron/local-data-service.js:38) and receipts in electron/agent-op-receipts.js.
Recipe — change background concurrency

AGENT_WORKER_COUNT at src/hooks/useAgentWorkers.js:1. Lower to 1 to serialize background AI work (cheaper, easier to follow in the log); raise cautiously — each worker is a full agent loop burning tokens.

Recipe — change remote-command responsiveness

POLL_MS (15000), HEARTBEAT_MS (60000), LEASE_MS (180000) at the top of electron/cloud-gateway.js:1. Faster polling = snappier remote commands but more Firestore reads (billing). Keep LEASE_MS comfortably above the longest expected run claim gap.

Calendar, placements & day planner

What you see

The Calendar overlay: a monthly grid with a daily detail column, a vertical day timeline (56 px per hour) where events and scheduled tasks sit as blocks, a quick-add field that understands "9am 90m Rehearse set", an add-from-picker for existing tasks, and a Plan my day action where the AI proposes a realistic schedule you can accept per-block.

How it works

  • Two kinds of blocks. Events are organizer items (type: 'event') with recurrence support — src/lib/recurrence.js:11 eventOccursOnDate(), ported from v1. Placements are time-slots referencing a task: "a placement contains time context only; the service joins the referenced task on every read, so title, priority, and completion never drift" (src/hooks/usePlacements.js:2; placements table from electron/local-data/schema/008_calendar_placements.sql).
  • Views: src/components/overlays/CalendarModal.jsx (month grid + day detail, reading useOrganizer()), src/components/calendar/DayTimeline.jsx (the timeline; HOUR_HEIGHT = 56 at line 1), src/components/calendar/AddFromPicker.jsx (schedule an existing task/project).
  • Quick-add parsing: src/lib/calendarQuickAdd.js:13 parseCalendarQuickAdd() — leading time, optional duration with units from UNIT_MINUTES (m/min/h/hr/hours…), rest becomes the title.
  • Day planner: src/hooks/useDayPlanner.js + src/lib/dayPlanner.js — buildDayPlannerPrompt() packs the date, existing events/placements, open tasks (completed/cancelled excluded), and Forest projects into one JSON prompt; a headless agent turn returns proposals + a summary; accepting a proposal calls createPlacement. Governed by the day-planner skill's "read before you claim" rule.
  • Prioritizer hand-off: when the prioritizer picks a winner, a briizos-plan-priority-today window event opens the Calendar pre-focused on that candidate — src/App.jsx:847.
Recipe — denser or roomier timeline

HOUR_HEIGHT = 56 at src/components/calendar/DayTimeline.jsx:1 — pixels per hour. 40 = compact overview, 80 = touch-friendly. Blast radius: purely visual; block positions are computed from this constant so everything scales together.

Recipe — teach quick-add new duration words

Add entries to UNIT_MINUTES at src/lib/calendarQuickAdd.js:1 — e.g. d: 1440 for day-length blocks. Keys are the suffixes users type; values are minutes.

Organizer & sticky Notes

What you see

The Organizer overlay: one unified manager for notes, events, timers, and projects (📝 📅 ⏱️ 📁 icons), with tags and done-toggles. The Notes widget: a sticky-note drawer docked right, from which notes tear off and float anywhere.

Sync: SQLite, Firestore & the SyncContract

The rule of the land

The authoritative contract is ../SyncContract.md (parent directory, shared with the Web repo). Its core invariant, in plain words: information and appearance are stored separately.

  • users/{uid}/organizer/{itemId} — the information: title, body, color, tags, status, dates. Source of truth (§2.1).
  • users/{uid}/panels/{panelId} — the appearance: position, size, minimized state, per-platform geometry (ui.local.xywh vs ui.web.xywh). "Render state only. Not an information source" (§2.2).
  • Each points at the other (orgId ↔ panelId); deleting a note deletes both; hiding a panel touches only render state (§2.7–9). Legacy aliases (content, name, top-level x/y/w/h) may be read for migration but never written (§2.10).

Implementation

  • The canonical pair of functions: src/lib/briizSyncCore.js — readBriizSyncState() (line 122: normalize both collections, compose notes only from organizer docs, report orphan panels separately) and prepareBriizSyncWrite() (line 245: emits explicit Firestore operations; rejects panel writes lacking orgId). Per contract §6, the same logic exists verbatim in the shared FINALSYNC module.
  • Adapters: src/lib/syncAdapters.js — task/organizer/calendar/note doc shapes with required-field checks and timestamps.
  • The Firestore module: src/lib/firestore.js (2,270 lines) — subscriptions and CRUD for notes (line 320+), tasks (569+), schedule (1083+), projects (1305+), chat mirrors, sessions, and automated-task claiming — all under users/{uid}/… via getUserCollections() (line 190).
  • Continuity backup: the cloud gateway chunks and mirrors three local domains — tasks, organizer, retainedText — for device recovery/promotion (electron/cloud-gateway.js:6; cloud:restore-continuity/cloud:promote-device IPC).
Caution

Any change to how notes, organizer items, calendar data, or app state are stored must pass through the contract's read/write rules (§§4–5). Cosmetic and UI changes are exempt — position/size is the panel doc's job. When in doubt: if the edit changes what gets written to Firestore, re-read SyncContract.md first. This is also CLAUDE.md hard rule #2.

Authentication

Firebase email/password. src/context/AuthContext.jsx:1 manages the session (sign in/up/out, ID-token refresh, 20-second request timeout at line 10); src/components/LoginOverlay.jsx covers the workspace whenever unauthenticated (mounted last in the shell, src/App.jsx:1123). Notably, the local experience (layout, SQLite data, most panels) works regardless — auth gates the cloud: Firestore sync, remote commands, agent job claiming.

Bfast (toasts, snackbars, Margerin)

The app's notification family, mounted once at the shell root (src/App.jsx:1126). Its brain is deliberately not React: src/lib/bfast-queue.js:1 holds one ordered queue of pending actions in three kinds:

  • toast — fire-and-forget notice (toast('…') from anywhere).
  • snackbar — notice with an action button.
  • margerin — the signature piece: a pre-hoc intent hold. A pill appears holding an unresolved Promise until you commit ✓ (approve, the default), ✕ (reject), or 💬 (discuss). Click the pill to commit the selected icon, click a specific icon to commit that one, or scroll-wheel over the pill to rotate the selection — full interaction spec in the header of src/components/bfast/Margerin.jsx:1. This is how agent tool confirmations reach you.
